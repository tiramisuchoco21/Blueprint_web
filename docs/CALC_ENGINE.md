# 청사진 — 계산 엔진 명세 (Rule Engine + Calculator)

`청사진_페르소나1_2_최종수정본.pdf` 기준. **LLM이 개입하지 않는 영역**이지만, 여기서 나온 숫자가 곧 Numeric Guard의 화이트리스트이므로 AI 설계의 전제가 된다.

---

## 0. ⚠️ 먼저: 문서 3세대가 서로 충돌한다

받은 자료를 시간순으로 놓으면 **의도적인 방향 전환**이 보인다. 구세대 문서를 그대로 구현하면 최신 원칙과 정면충돌한다.

| 항목 | 1세대 `초안.pdf` / `시나리오 1탄·2탄` | **2세대 `페르소나 최종수정본` / `MVP 설계서`** |
|---|---|---|
| 소비 분석 | "LLM이 **스트레스성 감정 소비를 판별**", "확률 85%" | **금지.** "심리상태를 확률로 단정하지 않는다" → 규칙 기반 지수 |
| FinTox 점수 | 85점 (감정 소비 위험군) | **72점** (규칙 기반 주의) |
| 페르소나1 주력 정책 | **중기청 전월세보증금대출** (연 1.5%, 8천만) | **신규지원 종료 → 추천 목록 제외** |
| 저축 수단 | **청년도약계좌** 월 50만 (정부기여금) | **신규가입 종료 → 제외** |
| 정책 범위 | 240개 지자체 조례 전체 RAG (ChromaDB) | **10~15개 핵심 정책 정형 DB** |
| 영수증 OCR | Tesseract 포함 | **P2로 강등** |
| 투자 비교 | S&P500 / 배당ETF 세후 수령액 시뮬레이션 | **삭제됨** |
| 모델 | Claude 3.5 Sonnet / GPT-4o-mini | 미지정 (`GPT 또는 Claude`) |

### 구현 지침

1. **2세대 문서를 단일 진실원천으로 삼는다.** 1세대는 배경 이해용.
2. **중기청·청년도약계좌는 "삭제"가 아니라 "종료 상태로 DB에 남긴다".** MVP 설계서 p.5의 `Ended ⚫` 워터폴 상태가 바로 이 두 건을 보여주기 위한 장치다. **1세대가 주력으로 밀던 정책이 2세대에서 종료 처리된 것 자체가 시연의 핵심 장면**이다 — "다른 서비스는 아직도 이걸 추천합니다"라고 말할 수 있다.
3. **"감정 소비 LLM 채점"은 구현하지 마라.** 1세대 HTML 프로토타입(`시나리오 1탄.pdf` p.7~19)에 `감정 소비 주의 (85%)` UI가 남아 있다. 그대로 재사용하면 2세대 원칙 위반이다. **해당 컴포넌트는 반드시 교체한다.**
4. **S&P500 비교는 되살리지 마라.** 투자 권유 소지가 있고, 금융 AI 신뢰 설계와 충돌한다. 2세대가 뺀 건 의도적으로 보인다.

## 1. 페르소나 1 — 전세 자기자본 역산

### 1.1 계산 체인

```python
# app/engine/calculator.py
def jeonse_plan(p: UserProfile, policy_cap: int) -> FeasibilityResult:
    required_equity = p.target_amount - policy_cap          # 1억  − 8,000만 = 2,000만
    gap             = required_equity - p.current_cash       # 2,000만 − 600만  = 1,400만
    required_monthly= ceil_won(gap / p.horizon_months)       # 1,400만 ÷ 24     = 583,333
    ...
```

| 항목 | 산식 | 값 |
|---|---|---|
| 희망 전세보증금 | 입력 | 100,000,000 |
| 버팀목 이론상 상한 | `min(보증금 × 0.80, 상품한도 1.5억)` | 80,000,000 |
| 목표 자기자본 | `보증금 − 정책대출` | 20,000,000 |
| 현재 보유자금 | 입력 | 6,000,000 |
| 추가 필요자금 | `자기자본 − 보유` | 14,000,000 |
| 24개월 월 저축목표 | `1,400만 ÷ 24` | **583,333 (≒58.3만)** |

> ⚠️ 설계서 본문은 `월 58만`, MVP 설계서 대시보드는 `583,000`으로 표기가 갈린다. **`583,333`을 정본으로 하고 UI 표시만 반올림**한다. Numeric Guard 화이트리스트에는 `583333`, `583,000`, `58만`, `58.3만`을 **모두** 넣어야 한다. 이런 표기 변형이 Guard 오탐의 1순위 원인이다.

### 1.2 놓치면 안 되는 축: **학자금대출 400만 원**

페르소나 1은 학자금대출 잔액 400만 원을 갖고 있는데, 위 계산 어디에도 안 들어간다. 두 가지 중 하나를 **명시적으로** 선택해야 한다.

| 처리 | 결과 |
|---|---|
| (a) 자기자본에서 차감 | 실질 가용 자기자본 2,000만 − 400만 = 1,600만 → 월 저축목표 상승 |
| (b) 별도 부채로 관리, 전세대출 심사 시 DTI 반영 항목으로만 표시 | 위 계산 유지 |

**(b)를 권한다.** 문서의 58만 원 숫자가 유지되고, 대신 대시보드에 `보유 부채: 학자금 400만 (전세대출 심사 시 반영 가능)`을 별도 카드로 노출한다. → "부채를 못 본 게 아니라 분리해서 관리한다"가 된다.

### 1.3 정책 워터폴에 실제로 넣을 정책 (페르소나 1)

| 정책 | 판정 | 근거 |
|---|---|---|
| 청년전용 버팀목전세자금 | 🟢 **Eligible** | 만 19~34 / 연소득 5,000만 이하 / 무주택 예비세대주 |
| 서울시 청년 임차보증금 이자지원 | 🟢 Eligible (비교 대상) | 한 상품만 추천하지 않고 **비교**한다 |
| 청년미래적금 | 🟡 **Conditional** | **3년 만기 ↔ 목표 24개월 불일치** ← §3 참조 |
| 청년수당 (상용근로자) | 🔴 Not Eligible | 재직 중 |
| 중소기업취업청년 전월세보증금대출 | ⚫ **Ended** | 신규지원 종료 |
| 청년도약계좌 | ⚫ **Ended** | 신규가입 종료 |

→ **4가지 상태가 전부 한 화면에 나온다.** MVP 설계서 p.5의 워터폴이 페르소나 1 하나로 완성된다.

## 2. 페르소나 2 — 매수 가능성 판정 (계산이 훨씬 무겁다)

내 초기 설계에 **없던 계산이 4개** 있다.

### 2.1 신용대출 상환 시나리오 비교 ← 신규

```python
# app/engine/scenarios.py
def compare_debt_repayment(p) -> DebtDecision:
    keep  = {"cash": p.assets,                 "annual_interest": p.loan * p.loan_rate}
    repay = {"cash": p.assets - p.loan,        "annual_interest": 0}
    # 연 5.2% × 2,500만 = 130만 원/년 절감
    return DebtDecision(
        recommend="REPAY",
        interest_saved=int(p.loan * p.loan_rate),      # 1,300,000
        cash_reduced=p.loan,                            # 25,000,000
        rationale_key="DTI_AND_CAPACITY",
    )
```

⚠️ **`recommend`는 룰이 정한다.** LLM에게 "갚는 게 나을까요?"를 묻지 않는다. 판단 기준을 코드로 박고, LLM은 그 결과를 서술만 한다. 문서도 *"무조건 상환이 아니라 주택구입 가능액·DTI·필요현금을 함께 계산한 결과"*라고 못 박았다.

### 2.2 조달 가능금액 체인

| 항목 | 산식 | 값 |
|---|---|---|
| 현재 금융자산 | 입력 | 200,000,000 |
| 신용대출 상환 | `− 25,000,000` | 175,000,000 |
| 12개월 추가저축 | `200만 × 12` | 24,000,000 |
| **1년 뒤 예상 현금** | | **199,000,000** |
| 정책대출 상품상 최대 | `min(LTV한도, DTI한도, 상품한도 3.2억)` | 320,000,000 |
| **총 조달 가능금액** | | **519,000,000** |
| 6억 대비 부족액 | `600,000,000 − 519,000,000` | **81,000,000** + 부대비용 |

### 2.3 LTV / DTI 제약 ← 신규

```python
def policy_loan_cap(house_price, income, rate, months, product) -> int:
    ltv_cap = int(house_price * product.ltv_max)          # 수도권 70%
    dti_cap = dti_limit_to_principal(income, product.dti_max, rate, months)
    return min(ltv_cap, dti_cap, product.max_loan)        # 상품한도 3.2억
```

**5억 주택 검증:**
- LTV 70% → 3.5억 / 상품한도 3.2억 → `min` = **3.2억**
- DTI 60%: 연소득 8,400만 × 0.6 = 5,040만/년 = 월 420만 여력. 실제 월 원리금 145만 → **통과**
- 필요 자기자본 = 5억 − 3.2억 = **1.8억**, 예상현금 1.99억 → **잔여 1,900만 (부대비용 버퍼)** ✓ 문서와 일치

### 2.4 원리금균등상환 ← 신규

```python
def monthly_payment(principal: int, annual_rate: float, months: int) -> int:
    r = annual_rate / 12
    if r == 0: return principal // months
    factor = (1 + r) ** months
    return round(principal * r * factor / (factor - 1))
```

**검증:** 3.2억 / 연 3.55% / 360개월 → **1,445,889원 ≒ 약 145만 원** ✓ 문서의 "월 원리금 약 145만 원"과 일치.
(이 문서 초판에 1,445,838로 적었던 것은 손계산 오차다. 실제 구현 결과는 1,445,889이고 `test_monthly_payment_matches_persona_doc`이 이 값을 고정한다.)

### 2.6 취득부대비용 ← 신규 (문서가 "별도"라고만 하고 금액을 안 줌)

```python
def acquisition_costs(price: int, cfg: CostConfig) -> dict:
    return {
        "acquisition_tax": int(price * cfg.acq_tax_rate),   # 생애최초 감면 여부 분기
        "brokerage":       int(price * cfg.brokerage_rate),
        "registration":    int(price * cfg.registration_rate),
        "moving":          cfg.moving_flat,
    }
```

⚠️ **요율을 코드에 박지 마라.** 문서 p.12가 *"고정된 정책 금리·할인율·발행일은 백엔드 상수로 박지 않고 RAG/API 조회값으로 관리"*를 요구한다. `cost_config.json`으로 빼고 **출처·기준일을 함께 표시**한다. 생애최초 취득세 감면은 요건·한도가 자주 바뀌므로 반드시 조회값으로.

MVP에서는 **총액을 단정하지 말고 범위로** 보여주는 게 안전하다: `취득부대비용 약 OOO만~OOO만 원 (기준일 2026-09-01, 출처 O)`

### 2.7 Plan A / Plan B 역산

```python
def plan_a(p) -> dict:   # 기간 고정 → 가능한 집값 역산
    for price in range(400_000_000, 700_000_000, 10_000_000):
        cap = policy_loan_cap(price, ...)
        if price - cap <= p.expected_cash - reserve(price):
            best = price
    return {"kind": "KEEP_HORIZON", "adjusted_target": best}   # → 4.8~5.0억

def plan_b(p, target) -> dict:   # 집값 고정 → 필요 기간·자본 역산
    gap = target - (p.expected_cash + policy_loan_cap(target, ...))
    return {"kind": "KEEP_TARGET",
            "extra_capital": gap,                       # 8,100만
            "extra_months": ceil(gap / p.monthly_saving)}
```

> **"6억을 포기하세요"가 아니라 "기간과 가격 중 무엇을 우선할지 선택하세요"** — 문서의 이 문장이 UX 카피의 정본이다. LLM 프롬프트에 그대로 넣어라.

## 3. 놓치기 쉬운 판정 축: **상품 만기 ↔ 목표시점 적합성**

페르소나 1의 청년미래적금 케이스다. 문서가 별도 항목으로 강조했다.

> *"청년미래적금은 3년 만기 장기 자산형성 상품이므로 D-24개월 전세자금 목표와 만기가 맞지 않는다."*

**자격은 되는데 목표에 안 맞아서 추천하지 않는다** — 이건 단순 자격 룰로는 절대 안 나온다. 별도 룰이 필요하다.

```python
# app/engine/rules.py
def maturity_fit(policy: dict, p: UserProfile) -> RuleCheck:
    m = policy.get("maturity_months")
    if m is None:
        return RuleCheck(field="maturity", passed=True, label="만기 제약 없음")
    ok = m <= p.horizon_months
    return RuleCheck(
        field="maturity",
        label=f"상품 만기 {m}개월 ≤ 목표 {p.horizon_months}개월",
        required=f"<= {p.horizon_months}", actual=str(m), passed=ok,
        note=None if ok else "목표 시점에 현금화 불가 — 목표자금 수단에서 제외, 장기자산으로 별도 검토",
    )
```

정책 레코드에 `"maturity_months": 36`, `"liquidity": "locked"`를 추가한다.

> **이게 MVP 설계서 USP 03(Goal Feasibility Engine)의 진짜 사례다.** "받을 수 있는 정책"과 "내 목표에 쓸 수 있는 정책"이 다르다는 걸 보여주는 유일한 장면이므로, 워터폴에서 🟡 Conditional로 반드시 노출해야 한다.

## 4. A8 — 비금융 신용 빌드업 (내 기존 설계에 누락)

페르소나 1 Step 4. 1세대·2세대 문서 양쪽에 살아있다.

```
통신비·건강보험료·국민연금 성실납부 정보 입력
  → "비금융정보 신용평가 반영 가능 항목 발견"
  → NICE/KCB 제출용 안내
```

| 구성 | 담당 | 비고 |
|---|---|---|
| 납부 문자 파싱 | 정규식 → LLM 폴백 | FinTox 파서(A6) **재사용** |
| 반영 가능 항목 판정 | **룰** | KCB/NICE 인정 항목 체크리스트 |
| 제출 안내문 생성 | LLM (A8) | 표준 텍스트 |
| **신용점수 상승폭** | ❌ **계산·표시 금지** | 문서 명시: *"신용점수 +20점, 승인확률 98%처럼 확정하지 않는다"* |

**우선순위: P2로 미루는 걸 권한다.** 150초 시연 동선(MVP 설계서 p.15)에 안 들어가고, AI 기여도도 낮다. 퀘스트 항목(`+20 XP`)으로만 남겨두면 화면에서는 존재감을 유지할 수 있다.

## 5. 퀘스트 XP — 두 문서가 다르다

| 출처 | 배점 |
|---|---|
| MVP 설계서 p.11 | 전 항목 `+20 XP` 균일 |
| 페르소나 최종본 p.6 | `목표설정 +30`, `자동저축 +30`, `자격체크 +20`, `K-패스 +10`, `FinTox 3회 +10` |

**페르소나 최종본(차등 배점)을 채택한다.** 행동의 중요도가 점수에 반영되는 쪽이 게이미피케이션으로 더 말이 된다. 레벨 명칭도 페르소나 2 기준으로: `Lv.1 예비신혼 → Lv.2 주택준비 부부 → Lv.3 매수 준비완료`.

> 두 문서 모두 **"레벨은 대출 승인 가능성이 아니라 재무준비도(Financial Readiness)"**를 명시한다. 이 문구는 UI에 상시 노출한다.
